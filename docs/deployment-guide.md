## 検証と展開の流れ

各段階は「前段では見つからない種類の問題」を担当しています。飛ばすと後段でまとめて出ます。

| # | 段階 | ここで初めて分かること | 手段 |
|---|------|------|------|
| 1 | 構文チェック | 構文エラー・クォート漏れ | `bash -n` / `shellcheck`、PowerShell はパーサ（CI 未組み込み・ローカル実施） |
| 2 | CI でのスクリプト検証 | ロジック（状態遷移が仕様どおりか） | [verify-scripts](../.github/workflows/verify-scripts.yml) が push / PR で自動実行 |
| 3 | 試験機での直接実行 | OS・シェル・パッケージマネージャーの導入形態の差 | 試験機で `scripts/run-{macos,windows,wsl}-verify` を実行 |
| 4 | 試験機へ MDM 経由で投入 | **MDM 仕様の差**（実行ユーザー・実行頻度・タイムアウト） | 対象 MDM に登録し試験機1台へ配信 |
| 5 | テストユーザー数名へ投入 | **実利用者の環境差**（rc の内容・シェル統合・バージョンマネージャー） | パイロットグループへ配信 |
| 6 | 全体展開 | — | 対象グループを拡大 |

- **3 → 4 で落ちる理由**: 検証ヘルパーは実行者の権限で動きますが、MDM は macOS なら root、Iru の Windows なら SYSTEM で実行するため、読み書きする設定の持ち主が変わります（[実行コンテキスト](design.md#実行コンテキスト)）
- **4 → 5 で落ちる理由**: 利用者の `.zshrc` 等にある各自のバージョンマネージャーやシェル統合が、PATH 解決や出力解析に影響します
- 各段階の確認は [動作確認コマンド](troubleshooting.md#動作確認コマンド) と MDM コンソールのステータスで行い、切り戻しは各手順ページの解除スクリプトを配信します（管理対象のキーのみ削除）
- 現状把握だけ先に行う場合は、投入を登録せず検出・拡張属性・監査のみ配信します
